Shipping this exposed a genuinely dangerous cold-start bug, caught before it hit production: with no watermark yet, unbounded cursor pagination has no natural stopping point short of a ticker's *entire trade history* - every watched ticker would page up to the hard safety ceiling, simultaneously, on every single restart.

The fix that shipped anyway (before the cold-start guard was added) caused a real, live second incident. Removing the 100-item cap multiplied real per-tick trade volume 10-30x, and two existing functions on that exact hot path - series_evaluator.record_trade_observed() and candidate_log.record_rejection() - each open a brand-new SQLite connection (with a CREATE TABLE IF NOT EXISTS check) per individual raw trade. Thousands of those in one tick, each a synchronous blocking call, froze Python's single-threaded asyncio event loop for several minutes - confirmed via nginx logging "upstream timed out" on /api/state, and an internal request timing out against localhost:8000 from inside the very same container. Not a network/rate-limit issue, a request-handling process that could no longer do anything else at all while it worked through the backlog.

Raised the question directly: given this, should the app move off SQLite entirely to a real DB server? Answered with AskUserQuestion rather than unilaterally either rewriting the persistence layer or dismissing the concern - the actual bug was blocking I/O running on an async event loop, not a SQLite capacity ceiling; a DB server wouldn't have prevented the identical mistake. Recommendation (finish hardening SQLite properly) confirmed. Three-part fix: (1) _fetch_trade_tape() now pages every ticker to true completion via a new _fetch_trades_for_ticker(), stopping only on Kalshi's own empty-cursor signal - except when there's no watermark yet (the very first tick after any restart), where it deliberately fetches one page and stops; a new state["trade_tape_last_fetch_ts"] watermark makes every subsequent tick a small, bounded incremental fetch instead. The Trade Tape UI panel keeps its own 100-item display cap, now fully decoupled from whale detection's input, which is genuinely uncapped. (2) kalshi_trade_tape.fetch_signals() restructured so its entire per-trade loop - every blocking call it makes, not just the two above - runs inside a new synchronous _process_trades_sync() dispatched via asyncio.to_thread(), so no volume of real trade data can ever again block request handling. series_evaluator. record_trades_observed_bulk() collapses what used to be one SQLite connection per trade into one per tick (counts pre-aggregated per series in Python first).
