phase 151 · crash-alert resolution, and a correction

"crash" alerts can finally resolve — and a stale claim about why they mattered gets fixed

Phase 149 logged, but didn't fix, a real gap: services/alerting/alerting.py's "crash" category (recorded by task_supervisor.py's exception handler) had no resolution path anywhere — resolve_category was only ever called for the two continuously-monitored transition-based conditions (kill_switch, stream connectivity), so active_alerts() included every historical crash forever. phase 153 · the CI guard from phase 152 was itself the noise source

A check that cried wolf every fifth commit is why nobody noticed it was red

Phase 152 found quality-architecture-audit red across three consecutive pushes (d644034, 21a303a, b28a380) with nobody noticing, and fixed the instance by regenerating static/project-manifest.json. It did not ask why nobody noticed. This phase did, after the same failure recurred twice more in one session.

Root cause was in tools/project_manifest.py, and it was a gap between a documented intent and its implementation rather than a bug. _CHURN_FIELDS' own comment states the goal — "the check should gate structural facts, not require a manifest commit on every unrelated code commit merely because SHA changed" — but it excluded only generated_from_head and generated_at. Line and test counts churn nearly as reliably as the SHA does, and they were still compared for exact equality. Measured across 25 commits of origin/main: lines.python changed on 21% of them and tests.count on 21%, each time by a fraction of a percent. So roughly one commit in five reded this pipeline over a number no reader could be misled by, and the only remedy was ever to re-run --write and commit the result — git log on the manifest shows those chore commits accumulating verbatim ("Regenerate stale project-manifest.json (fixes red architecture-audit CI)"). The alarm fatigue was not a side effect of that; it was phase 152's unexplained "nobody noticed".

--check now compares against a 10% relative tolerance instead of exact equality, and prints sub-threshold drift rather than suppressing it, so accumulation stays visible instead of appearing only when it trips. Thresholds were chosen from the same measurement, not picked: total drift over those 25 commits was 3.1% (lines.python) and 4.1% (tests.count), leaving real headroom. Verified by fault injection both ways — the actual historical staleness this guard exists for ("5,189 lines / 29 files / 20 API routes" against a repo an order of magnitude past it) still fails loudly at +896.4%/+682.8%/+370.0%, while the phase 152 case itself (four new files, 1.8% drift) now passes with the drift reported. That second half is a deliberate trade, not an oversight: four files in 227 misleads nobody, and treating it as a hard failure is precisely what taught everyone to stop reading this check. Key sets, schema_version, and any 0→nonzero change stay exact — a tolerance must never absorb a schema change. Comparison logic was extracted into a pure, unit-tested compare() rather than left inside the CLI, per the CI-guardrail rule that a checker's logic shouldn't live only in its command-line plumbing; nine new tests pin the behavior. The failure message now also prints the regeneration command, including the non-obvious part that it must run on the host — the container image has no git binary, so ddev exec silently writes generated_from_head: null.
