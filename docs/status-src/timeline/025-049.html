phase 28 · /api/state efficiency pass, plus two real bugs caught live along the way

"Make data consumption, storage, and retrieval hyper-efficient" - measured before touching anything

Direct request, but deliberately investigated before implementing anything - the request named "storage" as a concern, and data/*.db turned out to be a red herring: 332KB total, and PRAGMA freelist_count showed most of even signal_log.db's share was empty pages left over from testing phase 27's reset-domains feature minutes earlier, not organic growth. The real weight was GET /api/state itself: 43.8KB per fetch, polled every 5s (setInterval(refresh, 5000)) regardless of whether the backend's own poll_interval_sec (15s default) had produced anything new - meaning roughly two of every three polls re-sent and re-parsed byte-for-byte identical data. Follow-up clarification from the requester ("keeping polling intervals as short as possible... it's data latency I'm concerned about, not space") ruled out the tempting-but-wrong fix (just slow the frontend poll down) in favor of making an unchanged poll cheap instead of infrequent.

Fix: a state["generation"] counter, bumped once at the end of every trading-loop poll tick and by every control endpoint that mutates state outside the loop (/api/toggle, /api/risk/halt, /api/risk/resume, /api/reset, /api/config, /api/trading/enable, /api/trading/disable, and - caught by audit, see the bug below - GET /api/markets/search), used as /api/state's ETag. An unchanged poll now gets a 304 with no body instead of 43.8KB re-fetched and re-parsed; live curl confirmed a real 304 round trip. The response body itself is memoized per generation too, so signal_log.stats()/shadow.recent()/ shadow.stats() - real SQLite queries - now run once per actual change instead of once per HTTP request. One real-environment wrinkle caught live, not assumed: nginx's gzip module rewrites a strong ETag to weak ("2" → W/"2") on the way out, which silently broke a first, naive exact-string comparison - fixed with an RFC-7232-style weak comparison that strips a W/ prefix before comparing. Separately, account.fills/ account.positions - full raw Kalshi objects, 13.4KB of the 43.8KB, mostly serving debug tooltips and the raw-JSON detail view rather than the rendered rows themselves - got the same _slim_market-style trim (new _slim_position/_slim_fill, field names taken from exactly what renderRealPositions/renderRealFills already read, not re-guessed). WebSockets came up as an alternative and were deliberately deferred: the dominant latency source here is poll_interval_sec itself, not the polling transport, so the marginal win didn't clear the added complexity (reconnect/backoff, multi-tab fanout, an nginx Upgrade-handshake config change) - worth revisiting only if 15s-granularity updates still feel slow after this pass.

Two real bugs turned up during live verification of the above, both confirmed via Selenium, not assumed fixed from reading the diff. First, a genuine regression from the new caching itself: GET /api/markets/search writes into state["market_titles"] but wasn't bumping the new generation counter, so a freshly-searched market's resolved title wouldn't propagate to /api/state - and therefore to Open Positions or the detail modal - until the next real poll tick caught up some 15s later, reported live as titles "reverting" to raw tickers like KXITFMATCH-26AUG08PLEPAP-PAP. Fixed by adding the missing bump. Second, a pre-existing bug, unrelated to this pass but surfaced during the same live testing: the market- detail modal's "click outside to dismiss" backdrop handler only checked the click event's final target, but refreshMarketDetail() replaces the modal body's innerHTML on every poll tick while the modal is open - so a mousedown-then-mouseup that straddled one of those replacements got its click event retargeted by the browser to the backdrop itself (the nearest ancestor still in the DOM), silently closing the modal mid-interaction. Reported live as "refresh forces closing of modals while I'm trying to examine them." Fixed by also requiring mousedown to have started on the backdrop itself (new __backdropMouseDownOnSelf flag) before a click counts as "outside" - verified with a real mousedown → DOM-swap → mouseup race via Selenium ActionChains (modal stayed open) alongside a genuine outside click (still closes it, so the fix didn't just disable the feature).
