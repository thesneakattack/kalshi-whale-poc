## Checked and corrected during this pass

- Section 4's original benchmark design (barrier-raced multiple holders)
  produced an unhandled exception in a holder thread and a misleading
  headline note ("does not chain n_holders*hold_sec") that the crash
  itself contradicted. Rewritten as a deterministic two-holder handoff
  (`section4_chained_holders_vs_contender`); re-run clean, no exceptions,
  and the actual numbers now support the opposite, correct conclusion
  (chaining CAN exceed the nominal ceiling: 3s+3s holds make a 5s-ceiling
  contender raise; 2s+2s holds, summing under 5s, let it succeed).
- Section 1's original design synchronized the holder's release off the
  contender's own blocking call completing - a circular dependency that
  made the "releases early" case untestable and produced a false-ceiling
  reading (5.006s where 3.0s was expected). Fixed to a fixed
  `time.sleep(HOLD_SEC)`; re-run confirms the intended behavior (succeeds
  at 3.16s).
- Discovered mid-investigation that `series_evaluator.record_trades_observed_bulk()`
  is never actually called from live code - this invalidated the doc's
  first-draft claim that it was "the one real write" in
  `_process_trades_sync`. Corrected in both the doc and
  `bench/family2_busy_timeout_mechanism.py`'s docstring, and filed as its
  own issue (#621) rather than silently fixed or silently dropped.
- WAL-file-size figures were originally eyeballed as a rounded range
  ("4.1-4.7MB"); recomputed precisely from the actual byte counts already
  captured (3.93-4.46 MiB) and cited with the exact byte figures.
