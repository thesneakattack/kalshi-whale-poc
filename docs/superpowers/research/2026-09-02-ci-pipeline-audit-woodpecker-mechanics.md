## Summary (15 lines)

1. `when.path` is evaluated only for `push` + the three pull events (`constraint.go` 183-186); sub-keys are exactly `include`, `exclude`, `ignore_message`, `on_empty` (default **true**); `exclude` skips only when *every* changed file is excluded (3.5.0 #5042).
2. A workflow skipped by its own `when` never becomes a workflow row, so **no GitHub status is posted**; if all workflows are skipped the pipeline row is deleted and the response is 204 + `Pipeline-Filtered: true`. A step-level skip just drops the step; the workflow still runs and posts its status.
3. Changed files come from GitHub REST, not the webhook (3.11 #5618): PR = full PR file list (`ListFiles`, paginated); push = `CompareCommits(before, head)` (force-push/new branch → head commit only). The 500-file cap affects only `CI_PIPELINE_FILES`, never the filter; GitHub itself caps compare at 300 files / PR files at 3000.
4. `evaluate` = expr-lang, ANDed within a list item, ORed across items. Manual `variables` are visible to step-level `evaluate` but the workflow-level `when` is evaluated once *without* them in the builder — opt-in workflow selection by variable is inferred not to work; opt-out (`SKIP != "true"`) does.
5. Manual run: `POST /api/repos/{id}/pipelines` `{branch, variables, message}` (MustPush); commit = branch head via `GetBranch`; `Ref=refs/heads/<branch>` (3.18 #7051); no `changed_files`; variables land as bare env names in **non-plugin steps only** (3.18 #7040); no way to pick a single workflow/step. CLI: `woodpecker-cli pipeline create <repo> --branch B --var K=V`.
6. Cron: repo-level jobs (`/api/repos/{id}/cron`, MustPush) with `schedule`, `branch`, `timezone`, `enabled`, `variables`; `when.cron: <glob>` routes by job name at workflow or step level; runs at the branch head.
7. Workflows share nothing: each is its own clone, volume, network, queue task, agent slot, and GitHub context. `depends_on` supports `optional: true` (3.15); `runs_on` is deprecated for `when.status`. A dependency-skipped workflow is finalized as `skipped` → GitHub **`pending`/"unknown status"** (source-derived).
8. `[skip ci]`/`[ci skip]` (regex, case-insensitive, brackets required) applies to push + pull events only, checked against the push head-commit message or the **PR title**.
9. `cancel_previous_pipeline_events` cancels older **pending, running and blocked** pipelines of the *same event* and same branch (push) / same refspec (PR); a PR event never cancels a push pipeline. Superseded pipelines get `cancel_info.superseded_by`; running workflows end `killed` → GitHub `error`, never-started ones stay `pending` on that commit (inferred).

## 1. `when.path` — semantics, status on skip, sub-keys, events, changed-file computation, limits

### 1.1 Evaluation model (identical for workflow-level and step-level)

- A `when` block is a list of constraints. `When.Match` "Returns true if at least one of the internal constraints is true" (constraint.go 63-81); inside one list item every sub-key must match: "Match returns true if all constraints match the given input. If a single constraint fails a false value is returned." (constraint.go 168-217). The **same** `Constraint.Match` is used with `global=true` for the workflow-level block and `global=false` for steps; the only difference is that the `matrix` sub-key is applied for steps only (constraint.go 170-175).
- Docs (step-level wording): "If at least one of the conditions in the `when` block evaluate to true the step is executed, otherwise it is skipped. A condition is evaluated to true if _all_ sub-conditions are true." Docs (workflow-level wording): "If all conditions in the `when` block evaluate to true the workflow is executed, otherwise it is not included in the pipeline." The code shows the workflow-level list is still OR-across-items / AND-within-item; the global-section sentence is loose wording, not a different algorithm (constraint.go 64-81 has no `global` branch in the outer loop).
- `path` is only evaluated for push and pull events: `// changed files filter apply only for pull-request and push events` / `if m.Curr.Event.IsPull() || m.Curr.Event == metadata.EventPush { match = match && c.Path.Match(...) }` (constraint.go 183-186). `IsPull()` is true for `pull_request`, `pull_request_closed`, `pull_request_metadata` (pipeline/frontend/metadata/const.go 32-40). For `tag`, `release`, `deployment`, `cron`, `manual` the `path` sub-key is **ignored, i.e. treated as satisfied** (the `match &&` clause is never applied). Docs: "Path conditions are applied only to **push** and **pull_request** events." (the docs omit the two extra PR sub-events; the closed-PR case was added in 3.0.0, CHANGELOG "Apply changed files filter to closed PR [#4711]").

### 1.2 Sub-keys and defaults (`pipeline/frontend/yaml/constraint/path.go`)

```go
type Path struct {
	Include       []string              `yaml:"include,omitempty"`
	Exclude       []string              `yaml:"exclude,omitempty"`
	IgnoreMessage string                `yaml:"ignore_message,omitempty"`
	OnEmpty       optional.Option[bool] `yaml:"on_empty,omitempty"`
}
```
(path.go 29-34). Those four are the only keys. Shorthand: a plain string or list under `path:` is treated as `include` (path.go 37-66, `out2` appended to `Include`). Defaults: `on_empty` → **true** (`c.OnEmpty.ValueOrDefault(true)`, path.go 110); `ignore_message` → empty (disabled); `include`/`exclude` → empty.

Match algorithm, in this order (path.go 103-121):
1. If `ignore_message` is non-empty and the commit message contains it (case-insensitive substring) → **true** (all path conditions ignored, including `on_empty` — docs: "Passing a defined ignore-message like `[ALL]` inside the commit message will ignore all path conditions and the `on_empty` setting.").
2. If the changed-file list is empty → return `on_empty` (default true).
3. If `exclude` is set and **every** changed file matches at least one exclude pattern → **false** (`Excludes` returns true only when all files matched; path.go 134-148). Fixed to this semantics in 3.5.0 ("Fix exclude path constraint behavior [#5042]").
4. If `include` is set and **no** changed file matches any include pattern → **false** (path.go 124-132).
5. Otherwise **true**.

Patterns are `github.com/bmatcuk/doublestar/v4` globs (path.go import; docs link "glob patterns"). Docs example (verbatim):
```yaml
when:
  - path:
      include: ['.woodpecker/*.yaml', '*.ini']
      exclude: ['*.md', 'docs/**']
      ignore_message: '[ALL]'
      on_empty: true
```
Docs: "For pipelines without file changes (empty commits), you can use `on_empty` to set whether this condition should be **true** _(default)_ or **false** in these cases." (3.17.0 corrected this sentence: "docs: add note about `pull_request` events with `path` filter and correct comment about `on_empty` [#6819]").

### 1.3 What happens when a *workflow* is skipped by its path filter

- Build path: `builder.go` `genItemForWorkflow` runs `parsed.When.Match(workflowMetadata, true, environ)`; on no match it logs "marked as skipped, does not match metadata" and returns `nil, nil` — no `Item` is produced. Only produced items become persisted `Workflow` rows (`server/pipeline/items.go` `workflowsFromPipelineBuilder` iterates `pipelineItems`). Forge statuses are posted per persisted workflow (`server/pipeline/helper.go` 26-34 loops `pipeline.Workflows`; `server/rpc/rpc.go` `updateForgeStatus` posts for the one workflow it is given). **Therefore a path-skipped workflow posts no GitHub status at all** — consistent with the repo's documented finding for `quality-frontend-build` and with the branch-protection decision to exclude it.
- Workflows that `depends_on` the skipped one are also dropped, unless the dependency is `optional: true` (builder.go `items = filterMissingDependencies(items)`; utils.go 33-72; docs: "Other workflows that have a `depends_on` referencing a skipped workflow will also be excluded."). Optional deps arrived in 3.15.0 ("Support optional flag in depends_on for workflows and steps [#6461]").
- If **every** workflow is filtered: `server/pipeline/create.go` 124-131 deletes the just-created pipeline row (`_store.DeletePipeline`) and returns `ErrFiltered`; the HTTP layer answers **204 No Content with header `Pipeline-Filtered: true`** (`server/api/helper.go` `handlePipelineErr`: `c.Writer.Header().Add("Pipeline-Filtered", "true"); c.Status(http.StatusNoContent)`), for webhooks (hook.go 250-254) and for manual creation alike (pipeline.go 79-90).

### 1.4 What happens when only a *step* is skipped by its path filter

- `compiler.go` 237-247: a step whose `when` does not match is simply not added to the compiled config (`continue`). The workflow is still built, queued, executed and reports its own status like any other workflow. Skipped steps do not appear as step rows (they are never in `config.Stages`), so they neither run nor affect the workflow status.
- Edge case (**inference from source**): with the default clone step present, a workflow whose *every* step is path-filtered still yields one stage (the clone; compiler.go 159-182 adds it before the step loop) so `len(ir.Stages) != 0` (builder.go) and the workflow **runs clone-only and reports success**. `TestZeroSteps` in builder_test.go shows the "no item" outcome only with `skip_clone: true`. Falsifier: a live push touching nothing a step matches, on a workflow without `skip_clone`, that produces no workflow row.
- A step whose `depends_on` names a step filtered out by `when` is a compile error `ErrStepFilteredDependency` (compiler.go 272-284; 3.16.0 "pipeline: use more explizite error for step dependencies filtered out by its conditions [#6680]") unless the step dependency is `optional: true` (docs Workflows §Optional dependencies, last paragraph).

### 1.5 How changed files are computed (GitHub forge, `server/forge/github/github.go`)

- `Hook()` (679-715): for pull-request webhooks → `loadChangedFilesFromPullRequest`; for `push` → `loadChangedFilesFromCommits(ctx, repo, pipeline, currCommit, prevCommit)` with the comment "GitHub has removed commit summaries from Events API payloads from 7th October 2025 onwards." The webhook's per-commit `added/removed/modified` lists are **not** used any more.
- **pull_request** (717-761): GitHub REST `PullRequests.ListFiles` for the PR number, all pages (`for opts.Page > 0 ... opts.Page = resp.NextPage`), collecting both `filename` and `previous_filename`, then de-duplicated. So the list is the full PR diff, never "the last pushed commit" (docs: "`pull_request` events always contain all changed files of the pull request **not** just the files from the last pushed commit.").
- **push** (816-882): `curr = head_commit.id`, `prev = before` (parse.go 129). If `prev == curr` → logged error, no files. If `prev` is `0000…0` (branch creation / force-push per the code comment) or empty → `Repositories.GetCommit(curr)` → files of the **head commit only**. Otherwise `Repositories.CompareCommits(prev, curr)` paginated → files of the **whole pushed range** (base…head), de-duplicated. This is why the API shows populated `changed_files` on push pipelines (matches the "200 pipelines" observation you supplied). Relevant history: 3.11.0 "Switch to GitHub REST API to load changed files [#5618]", 3.12.0 "Fix workflow path filter for GitHub [#5721]".
- The list is stored on the pipeline (`ChangedFiles` → `changed_files` JSON, model/pipeline.go) and copied into metadata (`server/pipeline/metadata/metadata.go` 153).

### 1.6 Limits / degradation

- Woodpecker side: `maxChangedFiles = 500` (`pipeline/frontend/metadata/environment.go` 28-31). It caps **only the `CI_PIPELINE_FILES` env var**: with 0 files the var is `"[]"`, with ≤500 it is the JSON array, with >500 the variable is **not set** (123-134). Docs: `CI_PIPELINE_FILES` — "changed files (empty if event is not `push` or `pull_request`), it is undefined if more than 500 files are touched". The **`path` filter itself has no cap**: it matches against `m.Curr.Commit.ChangedFiles` directly (constraint.go 185).
- GitHub API side (not Woodpecker docs): PR files — "Responses include a maximum of 3000 files."; compare — "The list of changed files is only shown on the first page of results, and it includes up to 300 changed files for the entire comparison." Woodpecker's compare loop paginates, but per GitHub only page 1 carries files, so a single push range effectively yields ≤300 files (**inference** from the two documents together; not live-tested). Above those caps files are silently absent → an `include` filter can miss a real change and skip the workflow (fail-closed), whereas an empty list falls back to `on_empty` (fail-open).

## 2. `when.evaluate`

- Language: `github.com/expr-lang/expr` (constraint.go import line 23; docs: "The expression syntax can be found in [the docs](https://github.com/expr-lang/expr/blob/master/docs/language-definition.md) of the underlying library."). Compiled with `expr.Compile(c.Evaluate, expr.Env(env), expr.AllowUndefinedVariables(), expr.AsBool())` (constraint.go 202): the result must be a bool (else error "could not parse result"), undefined identifiers are allowed and evaluate as nil.
- Combination: `evaluate` is one more sub-condition of a list item — `match = match && bResult` (constraint.go 214) — so it is ANDed with `event`, `branch`, `path`, `cron`, … in the same item, and list items are ORed (§1.1). It can be freely combined with `path`/`event`/`branch` in one item. A compile/run error in the expression aborts the workflow build with an error (constraint.go 203-213; builder.go "pipeline config could not be parsed").
- Visible variables — docs: "Both built-in `CI_` and custom variables can be used inside the expression." In source the environment passed in is merged with `m.Environ()` (all `CI_*` metadata vars, constraint.go 196-201). What "custom variables" are visible depends on **where** the expression sits:
  - **Step-level** `when` (and clone/services `when`): evaluated once by the compiler with `whenEnv = c.env + c.nonPluginEnv` (compiler.go 124-126, 243; convert.go 153-155). `c.env` = metadata `CI_*` + server `WOODPECKER_ENVIRONMENT` globals (`WithMetadata`, `WithEnviron(b.Envs)`); `c.nonPluginEnv` = matrix axis + `AdditionalEnvs` (builder.go `toInternalRepresentation`: `compiler.WithNonPluginEnviron(axis)`, `compiler.WithNonPluginEnviron(b.AdditionalEnvs)`). `AdditionalEnvs` are the manual-run / cron `variables` (items.go 114: `AdditionalEnvs: currentPipeline.AdditionalVariables`). So manual variables **are** visible to step-level `evaluate`.
  - **Workflow-level** `when` is evaluated **twice**: first in the builder with `environ = metadata.Environ() + matrix axis + b.Envs` — **without** `AdditionalEnvs` (builder.go `genItemForWorkflow`: `environ := b.environmentVariables(...)`, then only `b.Envs` merged) — and then again in the compiler with `whenEnv` including `nonPluginEnv` (compiler.go 128). **Inference**: because the first pass sees the manual variable as undefined (nil), an "opt-in" expression such as `evaluate: 'ONLY == "tests-pytest"'` at workflow level is false in pass 1 and the workflow is dropped; an "opt-out" expression such as the docs' own example `evaluate: 'SKIP != "true"'` ("Skip step only if `SKIP=true`, run otherwise or if undefined") passes pass 1 and is honoured in pass 2 (an all-steps-skipped/empty config is then dropped). Falsifier: a live manual run with `variables: {ONLY: x}` and a workflow-level `evaluate: 'ONLY == "x"'` that does run.
  - `${VAR}` substitution (pre-processing) uses yet another set: `metadata.Environ() + axis + b.Envs` (builder.go, `metadata.EnvVarSubst(data, environ)`), so manual `variables` are **not** substitutable via `${VAR}`; an unknown `${VAR}` there errors at parse time (`TestMissingGlobalEnvsubst`) — which is the mechanism behind the repo's "unable to parse variable name" outage note in `quality-browser-e2e.yml`, and why `${i}`-style shell vars must be written `$${i}` (docs environment page: "`${variable}` expressions are subject to pre-processing. If you do not want the pre-processor to evaluate your expression it must be escaped" — `$${PATH}`).
- Scope column in the environment docs (3.17.0, #6879): variables marked `config` "can be referenced in `when` filters and expanded via string substitution"; `runtime`-only ones (`CI_STEP_*`, `CI_PIPELINE_STATUS`, `CI_WORKSPACE`) "cannot be used in `when` filters or substitutions".
- Docs examples (verbatim): `evaluate: 'CI_PIPELINE_EVENT == "push" && CI_REPO == "owner/repo" && CI_COMMIT_BRANCH == CI_REPO_DEFAULT_BRANCH'`; `evaluate: 'not (CI_COMMIT_MESSAGE contains "please ignore me")'`; `evaluate: 'CI_COMMIT_PULL_REQUEST_LABELS contains "deploy"'`.

## 3. Manual pipelines

### 3.1 REST endpoint and body

- `POST /api/repos/{repo_id}/pipelines`, auth `session.MustPush` (router/api.go 115; swagger summary "Trigger a manual pipeline"). Body `PipelineOptions`:
```go
type PipelineOptions struct {
	Message   string            `json:"message"`
	Branch    string            `json:"branch"`
	Variables map[string]string `json:"variables"`
} //	@name	PipelineOptions
```
(model/pipeline.go 117-121; identical in the live swagger `definitions.PipelineOptions`). `message` is new in 3.18.0 ("Allow to add custom message to manual pipelines [#6973]"). No other fields — in particular nothing to pick a workflow file, step, or commit.
- Handler (server/api/pipeline.go 52-92): decode → `lastCommit := _forge.BranchHead(user, repo, opts.Branch)` → `createTmpPipeline(model.EventManual, lastCommit, user, &opts)` → `pipeline.Create`. Response: 200 + Pipeline JSON; or via `handlePipelineErr`: **204 + `Pipeline-Filtered: true`** when no workflow matched (`ErrFiltered`), 404, 400, 500 (server/api/helper.go). 3.14.0: "Improve error message when no workflows for manual were found [#6313]".
- `createTmpPipeline` (pipeline.go 93-115) sets: `Event: manual`, `Commit: commit.SHA`, `Branch: opts.Branch`, `Ref: "refs/heads/" + opts.Branch` (3.18.0 fix "prefix manual trigger Ref with refs/heads/ [#7051]"), `Message: "MANUAL PIPELINE @ " + opts.Branch` or `"MANUAL: " + opts.Message + " @ " + opts.Branch`, `AdditionalVariables: opts.Variables`, `Author: user.Login`, `Timestamp: now`.
- `BranchHead` for GitHub = `Repositories.GetBranch(owner, name, branch, 1)` → `{SHA: b.GetCommit().GetSHA(), ForgeURL: ...}` (github.go 660-675): **the branch tip at trigger time**.

### 3.2 What the steps see

- `CI_PIPELINE_EVENT=manual`, `CI_COMMIT_SHA=<branch tip SHA>`, `CI_COMMIT_BRANCH=<branch>`, `CI_COMMIT_REF=refs/heads/<branch>`, `CI_COMMIT_MESSAGE="MANUAL PIPELINE @ <branch>"`, `CI_PIPELINE_AUTHOR=<triggering user login>` (metadata.go 129-161 copies these from the pipeline row; environment.go 94-102 emits them). `CI_COMMIT_REFSPEC`, `CI_COMMIT_PULL_REQUEST*` are unset (empty values are dropped, environment.go 198-204; 3.0.0 "Do not set empty environment variables [#4193]").
- `changed_files`: never loaded for manual (only `Hook()` loads them, §1.5) → absent from the pipeline JSON (`json:"changed_files,omitempty"`) → `CI_PIPELINE_FILES="[]"` (environment.go 125-126) and `path` filters are not evaluated at all for `manual` (§1.1). Docs: "empty if event is not `push` or `pull_request`".
- Checkout: the default clone step is `woodpeckerci/plugin-git` with `settings: {depth: "0"}` (compiler.go 161-164) and `CI_COMMIT_SHA`/`CI_COMMIT_BRANCH` in its env. plugin-git's `ref` flag reads **only** `PLUGIN_REF` (flags.go: `Sources: cli.EnvVars("PLUGIN_REF")`), `sha` reads `PLUGIN_SHA, CI_COMMIT_SHA`; with no `ref` setting `Exec()` takes the "fetch and checkout by commit sha" branch (`fetch(p.Pipeline.Commit, ...)` then `checkoutSha`) — so the clone pins the SHA recorded at trigger time, not whatever the branch points at when the agent starts.
- `variables` → environment: builder passes them as `compiler.WithNonPluginEnviron(b.AdditionalEnvs)`; the compiler merges `nonPluginEnv` into a step's environment **only if the step is not a plugin** (`if !container.IsPlugin() { maps.Copy(environment, c.nonPluginEnv) }`, convert.go 92-95). They arrive under their **bare key names** (no prefix, no transformation). 3.18.0 hardened this: "Don't inject additional env vars into plugins [#7040]" and "Don't inject matrix env vars into plugins [#7036]". They are not `${VAR}`-substitutable (§2). The docs do not describe manual `variables` semantics beyond the UI/CLI flag — **docs do not answer** the naming question; the statement above is source-only.
- Approval: `setApprovalState`/`needsApproval` (server/pipeline/gated.go) apply to manual pipelines like any other; with `require_approval: forks` a manual run by a repo user is not a fork PR and is not blocked (not exercised live; the repo's manual runs on 2026-08-28 evidently ran).

### 3.3 Can a manual run be restricted to one workflow / one step?

- Not by the API: there is no field for it (3.1). `PipelineBuilder.Build` iterates **every** YAML in `.woodpecker/` (builder.go); each workflow runs iff its `when` matches (`event: manual` must be listed — currently only `tests-pytest.yml` lists it, so a manual run of this repo builds exactly one workflow; the other five are filtered and post nothing, §1.3). If none matches → 204 `Pipeline-Filtered: true`.
- Emulation options (all source-derived, none live-tested here): step-level `when: - evaluate: 'ONLY == "" || ONLY == "pytest"'` works because step-level `evaluate` sees `variables` (§2); workflow-level selection only works in the opt-out form (`evaluate: 'SKIP_PYTEST != "true"'`) because of the builder's first pass without `AdditionalEnvs` (§2, inference). `path`/`ignore_message` cannot help for manual (§1.1).
- Related: the **restart** endpoint `POST /api/repos/{id}/pipelines/{n}` restarts an existing pipeline and injects **every non-reserved query parameter as an environment variable** (server/api/pipeline.go 591-604: `envs[key] = val[0]`, skipping `fork`, `event`, `deploy_to`); swagger description "Restarts a pipeline optional with altered event, deploy or environment". CLI: `woodpecker-cli pipeline start --param KEY=value` ("custom parameters to inject into the step environment").

## 5. `depends_on` between workflows, `runs_on`, shared workspace, `skip_clone`, `clone:`

### 5.1 `depends_on` (workflow level)

- Syntax: list of names, each a string or `{name, optional: true}` (constraint.DependsOn; docs Workflows §Optional dependencies, 3.15.0 #6461). The name is the file name "without the path, leading dots and without the file extension `.yml` or `.yaml`" (docs; `builder/utils.go` `SanitizePath`) — `depends_on: [tests-pytest]` for `.woodpecker/tests-pytest.yml`. 3.18.0 sorts files by name before building ("Sort workflow files by name [#7021]").
- Semantics: "A workflow doesn't execute until all of its dependencies finished successfully." Implementation: each workflow becomes one queue `Task` with `Dependencies = task IDs of its deps` and `RunOn` (server/pipeline/queue.go 30-81); the FIFO keeps a task in `waitingOnDeps` while any dependency is still pending/running (server/queue/fifo.go `filterWaiting`/`depsInQueue`), records each dependency's final status in `DepStatus` (`updateDepStatusInQueue`), and `Task.ShouldRun()` decides: with empty `RunOn` → run only if **every** dep status is `success`; `RunOn` ⊇ {success, failure} → always; `RunOn` = {failure} only → run only if **no** dep succeeded (server/model/task.go 69-106).
- What a dependent does when a dependency failed: it is not run; the scheduler hands it to the next polling agent through the skip callback, which locks it to that agent and calls `Done(taskID, rpc.WorkflowState{})` (server/rpc/rpc.go `Next`: "a skipped workflow is finalized through the regular Done flow"). `UpdateWorkflowStatusToDone` with `Started == 0` sets the workflow state to **`skipped`** (server/pipeline/workflow_status.go 47-62) and `Done` then posts a forge status for it (`s.updateForgeStatus(c, repo, currentPipeline, workflow)`). With GitHub's mapping (§9) `skipped` → commit state **`pending`**, description "unknown status". **Inference from these three files, not live-tested**: a required GitHub context whose workflow was skipped because a dependency failed is left in `pending` and never resolves. Falsifier: a live pipeline where a `depends_on` target fails and the dependent's context shows `error`/`failure`. This matters if the audit considers chaining the required contexts with `depends_on`.
- Missing dependency (file absent, or filtered out by its own `when`): the dependent is dropped from the pipeline before anything is queued (`filterMissingDependencies`, loops until stable), unless `optional: true`; `TestMissingWorkflowDeps`, `TestZeroStepsAsMultiPipelineTransitiveDeps`, `TestDependsOnOptionalFlag`. 3.17.0: "guard DAG cycle check against filtered-out optional dependencies [#6915]".
- Docs: "Workflows that need to run even on failures should set the `status` filter." → `when: - status: [success, failure]` at workflow level. Builder: if the workflow-level `when` includes `status: failure`, `"failure"` is appended to `RunsOn` (builder.go). Observation (source only): the second append uses `IncludesStatusFailure` again for `"success"`, so `status: [failure]` yields `RunsOn = [failure, success]` (= always run); `TestRunsOn` covers only `[success, failure]`. Not consequential for this repo (no workflow uses `status` at workflow level).
- `concurrency: {limit, group}` per workflow (3.x; docs Workflows §Concurrency) is unrelated to dependencies; noted only because it is the documented way to serialize a workflow across pipelines without cancelling.

### 5.2 `runs_on`

### 5.3 Workspace sharing between workflows

- No. Docs: "The workflows run in parallel on separate agents and share nothing."; "files are only shared between steps of the same workflow … you cannot access artifacts e.g. from the `build` workflow in the `deploy` workflow. If you still need to pass artifacts between the workflows you need use some storage plugin"; terminology: "Each workflow has its own isolated workspace, and often additional resources like a shared network (docker)." Source: each workflow is compiled with its own prefix `wp_<ulid>_<workflowID>` and gets `config.Volume = "<prefix>_default"` and `config.Network = "<prefix>_default"` (compiler.go 136-140; builder.go `WithPrefix`), and its own clone step (compiler.go 159-182). Each workflow is one queue task and consumes one agent slot (`WOODPECKER_MAX_WORKFLOWS` "Configures the number of parallel workflows."). So six workflow files = six clones, six default volumes/networks, six queue slots, six GitHub contexts per push/PR — exactly what `quality-browser-e2e.yml` already notes ("quality-frontend-build.yml is a separate Woodpecker pipeline with its own independent clone, so its build can't be reused here").
- Within a workflow: `workspace: {base, path}` — default base `/woodpecker`, path `src/<url-without-schema>` → e.g. `/woodpecker/src/github.com/thesneakattack/kalshi-whale-poc` (docs §workspace; `compiler.WithWorkspaceFromURL(compiler.DefaultWorkspaceBase, repo.ForgeURL)` in items.go). "The base attribute defines a shared base volume available to all steps. This ensures your source code, dependencies and compiled binaries are persisted and shared between steps." Plugins always see base `/woodpecker`.

## 6. `[skip ci]` / `[ci skip]`

- Docs: "Woodpecker gives the ability to skip individual commits by adding `[SKIP CI]` or `[CI SKIP]` to the commit message. Note this is case-insensitive."
- Source: `skipPipelineRegex = regexp.MustCompile(`\[(?i:ci *skip|skip *ci)\]`)` — square brackets are mandatory, spaces between the words optional, case-insensitive. `IsSkipCommitMessage(event, msg)` returns true only `if event == metadata.EventPush || event.IsPull()` (i.e. `push`, `pull_request`, `pull_request_closed`, `pull_request_metadata`); never for `tag`, `release`, `deployment`, `cron`, `manual` (constraint/skip.go 24-33).

- Interaction with the repo's required contexts: a skipped PR pipeline posts nothing, so the five required contexts would simply be absent on that commit (GitHub treats a missing required context as "expected/waiting").

## 7. `cancel_previous_pipeline_events`

- Docs (project settings): "By enabling this option for a pipeline event previous pipelines of the same event and context will be canceled before starting the newly triggered one." Server default for new repos: `WOODPECKER_DEFAULT_CANCEL_PREVIOUS_PIPELINE_EVENTS` = "`pull_request, push`" ("List of event names that will be canceled when a new pipeline for the same context (tag, branch) is created."). - Trigger point: `cancelPreviousPipelines` runs inside `start()` (server/pipeline/start.go 31-35), i.e. when the **new** pipeline actually starts — after config parsing, after the approval gate (a `blocked` new pipeline returns before `start`, create.go 135-137).
- Candidates = `GetActivePipelineList(repo)` = pipelines with `status IN (pending, running, blocked)` (server/store/datastore/pipeline.go). So **both running and pending (and blocked) older pipelines** are cancelled, not only running ones.
- Matching rule (cancel.go 117-130): the old pipeline must have the **same event** as the new one; for `push` the same `branch`; for every other event the same `refspec`. Refspec for GitHub PR events is `"<source>:<target>"` (parse.go 207) → a new commit on PR #N cancels the older still-active pipelines of PR #N. Consequences: a `pull_request` event never cancels a `push` pipeline of the same commit (event differs) and vice versa; two PRs targeting `main` from different branches do not cancel each other; a push to branch A does not cancel a push on branch B.
- What `Cancel()` does (cancel.go 30-95): evicts running+pending workflows from the queue (`Scheduler.CancelWorkflows`); pending workflows → `skipped`, their pending steps → `canceled`; running workflows are left for the agent ("Running ones will be set when the agents stop on the cancel signal" — agent `Wait` returns canceled, then `Done` with `Canceled=true` → workflow `killed`, steps `killed`; rpc.go `Done`, workflow_status.go 58-60, step_status.go 100-106). Pipeline status: `canceled` if it had only pending workflows, else `killed`; `finished = now`; `cancel_info.superseded_by = <new pipeline number>` (3.14.0 "Show cancellation reason in pipeline details [#6072]"; `CancelInfo{canceled_by_user, superseded_by, canceled_by_step}`). Related 3.14.0 fixes: "Fix pipeline cancellation status handling and step state synchronization [#6011]", "Allow to cancel on failure [#6158]" (`failure: cancel` on a step cancels the whole pipeline via `cancelPipelineFromStep`).
- GitHub side of a superseded pipeline: see §9.3.

## 8. Caching, images, and pipeline-structure guidance

### 8.1 Officially documented ways to avoid re-installing dependencies

1. **`volumes:` on a step, including named volumes** — "If you use the Docker backend, you can also use named volumes like `some_volume_name:/var/run/volume`." Requires trusted volumes: "Volumes are only available to trusted repositories and for security reasons should only be used in private environments." (linter enforces "Insufficient trust level to use `volumes`", linter.go 298-304). This repo has `trusted.volumes: true` and already uses `wp-uv-cache` / `wp-testmon-cache`. Host paths must be absolute. (3.6.0 docs: "Mention named volumes [#5130]".)
2. **Agent-wide default mounts** — `WOODPECKER_BACKEND_DOCKER_VOLUMES`: "List of default volumes separated by comma to be mounted to all pipeline containers (steps)." (docker backend docs). Not repo-scoped; mounts into every step of every repo the agent serves.
3. **Image pull policy** — "By default, Woodpecker does not automatically upgrade container images and only pulls them when they are not already present. To always pull the latest image when updates are available, use the `pull` option" (`pull: true` per step). Default therefore already avoids re-pulls of `python:3.13-slim`, `node:22-slim`, `selenium/standalone-chromium:138.0`, `mcr.microsoft.com/playwright/python:v1.62.0-noble`.
4. **Custom/pre-built base image** — any image from any registry is allowed (`image:` section; private registries via the registries feature). The docker backend "**will not** automatically remove images from the host. This task should be managed by the host system." (docker backend §Image cleanup). Combined with (3), a locally built image (e.g. `docker build` on the same host with all Python deps + git + Chrome deps baked in) is reused by every step that names it, with no registry push needed on a single-host agent. The docs do not describe a build-and-reuse workflow explicitly — **docs do not answer** beyond these two statements.
5. **Community cache plugin** — the plugin index lists "S3 Cache" (`quay.io/landre/woodpecker/cache`, author Loric André, source `https://codeberg.org/landre/woodpecker-plugins/cache`, community-maintained): download/upload/clear of paths to an S3-compatible bucket with branch/arch-keyed cache keys and gzip; it needs an S3 endpoint, so it is not a fit for a single-host setup that already has named volumes. No first-party cache plugin exists in the docs.
6. **Workspace** persists only across steps of one workflow (§5.3), so anything installed in a step is gone for the next workflow.
7. A `StepType` value `cache` exists in the model (model/step.go 65; the environment docs list `CI_STEP_TYPE` values "`commands`, `plugin`, `service`, `clone` or `cache`"), but no YAML keyword producing it is documented on any 3.18.x usage page — **docs do not answer**.

### 8.2 Guidance on structure (one workflow per check vs one workflow with many steps)

- Docs Workflows §"Benefits of using workflows": "faster lint/test feedback, the workflow doesn't have to run fully to have a lint status pushed to the remote"; "better organization of a pipeline along various concerns"; "utilizing more agents to speed up the execution of the whole pipeline". §"Status lines": "Each workflow will report its own status back to your forge."
- Cost of each extra workflow (source, §5.3): its own clone step, its own default volume and network, one queue `Task`, one `WOODPECKER_MAX_WORKFLOWS` slot while running, one GitHub status context, and no reuse of installed dependencies. Within one workflow, steps can run as a DAG (`depends_on` on steps → "all steps of the workflow will be executed in parallel besides the steps that have a dependency") sharing the workspace, at the cost of a single status context.
- There is no official "best practices"/"caching" page: the advanced-usage page (`90-advanced-usage.md`) contains only YAML anchors/aliases, map/sequence merges, "Environment data persistence" (write a file, `source ./envvars` in each step) and `WOODPECKER_ENVIRONMENT`. **Docs do not answer** the one-vs-many question beyond the bullets above.

## 9. Status reporting to GitHub

### 9.1 Context string

- Built by `server/forge/common/status.go` `GetPipelineStatusContext` from the Go template `WOODPECKER_STATUS_CONTEXT_FORMAT`, default `{{ .context }}/{{ .event }}/{{ .workflow }}{{if not (eq .axis_id 0)}}/{{.axis_id}}{{end}}`, with `context` = `WOODPECKER_STATUS_CONTEXT` (default `ci/woodpecker`), `event` = the pipeline event **except that `pull_request` is rendered as `pr`** (status.go 29-32), `workflow` = the workflow name (file name sanitized, §5.1), `axis_id` only for matrix workflows. Server docs list the variables `context, event, workflow, owner, repo` (the source also passes `axis_id`).
- Resulting contexts for this repo: `ci/woodpecker/push/<workflow>`, `ci/woodpecker/pr/<workflow>` (the five required ones), `ci/woodpecker/manual/<workflow>`, `ci/woodpecker/cron/<workflow>`, `ci/woodpecker/tag/<workflow>`, `ci/woodpecker/pull_request_closed/<workflow>`, `ci/woodpecker/pull_request_metadata/<workflow>` (only `pull_request` is abbreviated). Note the context is per **workflow**, not per pipeline: a manual run posts `ci/woodpecker/manual/tests-pytest` onto the branch-tip commit, which is a different context from the required `pr` ones.

### 9.2 One aggregate status?

- No. `Status()` is always called with a workflow and posts one `Repositories.CreateStatus` per workflow (github.go 576-607: `Context: GetPipelineStatusContext(repo, pipeline, workflow)`, `State: convertStatus(workflow.State)`); the callers loop over workflows (helper.go 26-34) or post for the workflow that just changed (rpc.go `updateForgeStatus`, comment "only do status updates for parent steps"). A pipeline-level summary status is an open TODO (builder.go: "TODO: add summary workflow that send status back based on workflows generated by matrix function depend on https://github.com/woodpecker-ci/woodpecker/issues/778"). Deployment events post a GitHub *deployment status* instead (github.go 582-596). Woodpecker uses the commit-status API, not the Checks API.

### 9.3 State mapping and what a killed/superseded pipeline leaves behind

- `convertStatus` (github/convert.go 50-61): `pending, running, blocked, skipped, canceled` → GitHub **`pending`**; `failure, declined` → **`failure`**; `success` → **`success`**; everything else — `killed`, `error` — → **`error`**. Description (status.go 58-77): killed → "Pipeline was canceled", error/failure → "Pipeline failed", blocked → "Pipeline is pending approval", skipped → "unknown status" (default branch).
- Posting moments: at creation/pending (`publishPipeline`, `updatePipelinePending`, `start` → each workflow `pending`), at workflow `Init` (running → still `pending`), at workflow `Done` (final state), and in `Cancel()` via `updatePipelineStatus(killedPipeline, …)`.
- **Inference (source-derived, not live-tested)** for a superseded pipeline: in `Cancel()` the pipeline object comes from `GetActivePipelineList`/`GetPipelineNumber` whose `Workflows` field is not loaded (`xorm:"-"`), `UpdateToStatusKilled` copies the struct, and the tree is only loaded *after* `updatePipelineStatus` (cancel.go 78-88) — so nothing is posted at cancel time. Running workflows are then finalized by the agent's `Done{Canceled:true}` → `killed` → GitHub **`error` / "Pipeline was canceled"**. Workflows that were still pending are set to `skipped` in the DB and evicted from the queue, no `Done` ever arrives, so their GitHub contexts remain **`pending`** on that (older) commit. Since GitHub evaluates branch protection on the PR's head commit, a superseded older commit's stale `pending` contexts do not block merging; they only look odd in the commit's status list. Falsifier: `GET /api/repos/1/pipelines?status=killed` plus the GitHub commit status of that commit showing all workflows updated at cancel time (this token could list killed pipelines but the shell was unavailable at that point, see final section).
- A workflow skipped because a dependency failed ends as GitHub `pending`/"unknown status" (§5.1). `blocked` (awaiting approval) is `pending`/"Pipeline is pending approval"; `declined` is `failure`.

## 10. REST API surface useful for cost auditing

All paths below are under `basePath /api` on `https://ci.webfoundry.dev` (swagger `host`/`basePath`). Auth tiers from `server/router/api.go`: repo routes require `MustPull` (public repo + this token: OK), some `MustPush`, global queue/agents/`/pipelines` require `MustAdmin`.

- **List pipelines** `GET /repos/{repo_id}/pipelines` (MustPull). Query: `page` (default 1), `perPage` (default 50), `before`/`after` ("only return pipelines before/after this RFC3339 date"), `branch`, `event` ("filter pipelines by webhook events (comma separated)"), `ref` ("strings contained in ref"), `status`. Returns `Pipeline[]` **without** `workflows` (list handler does not load the tree; the detail handler does: `pl.Workflows, err = _store.WorkflowGetTree(pl)`, pipeline.go 250-258).
- **Pipeline fields** (model/pipeline.go; swagger `definitions.Pipeline`): `id, number, author, parent, event, event_reason, status, errors, created, updated, started, finished, deploy_to, deploy_task, commit, branch, rerun_count, ref, refspec, author_avatar, forge_url, reviewed_by, reviewed, cancel_info{canceled_by_user, superseded_by, canceled_by_step}, workflows[], changed_files[], variables{}, pr_labels, pr_milestone, pr_draft, cron, from_fork, version, release, tag_title, title, message, timestamp, sender, author_email`. **Units**: `created/updated/started/finished` are `int64` **UNIX seconds** — the environment docs label `CI_PIPELINE_CREATED/STARTED` and `CI_PREV_PIPELINE_FINISHED` "UNIX timestamp", and the server writes them with `time.Now().Unix()` (pipeline_status.go 46, 55, 68-69, 75; step_status.go 52, 59, 80, 104). Live sample (pipeline #355): `created 1788370597, started 1788370605, finished 1788370648` (10-digit seconds). `started == 0`/`finished == 0` means not started/finished; queue wait ≈ `started - created`, wall time ≈ `finished - started`.
- **Pipeline detail** `GET /repos/{repo_id}/pipelines/{pipeline_number}` (MustPull; `latest` accepted as number) → same object plus `workflows[]`: `id, pipeline_id, pid, name, state, error, started, finished, agent_id, platform, environ, children[]` (model/workflow.go 19-33) and each step: `id, uuid, pipeline_id, pid, ppid, name, state, error, exit_code, started, finished, type` (`clone|service|plugin|commands|cache`) (model/step.go 26-40). Per-step durations = `finished - started` in seconds (rpc.go computes the Prometheus step-duration histogram exactly that way).
- **Step logs** `GET /repos/{repo_id}/logs/{pipeline_number}/{step_id}` (MustPull; `step_id` is the step's numeric `id`, not `pid`) → `LogEntry[]` = `{id, step_id, time, line, data, type}` with `type` 0 stdout, 1 stderr, 2 exit_code, 3 metadata, 4 progress (model/log.go 17-35). `data` is declared `[]byte`, which Go's `encoding/json` emits as a **base64 string** ("[]byte encodes as a base64-encoded string") — the swagger renders it as `array of integer`, which is the generator's approximation, not the wire format. 3.18.0 added `GET …/logs/{pipeline_number}/{step_id}/download` returning `text/plain` (one decoded line per entry; pipeline.go 315-344, changelog #6876) and "Return step logs strictly in line order [#6999]".
- **Pipeline config** `GET /repos/{repo_id}/pipelines/{pipeline_number}/config` (MustPull) → `Config[]` = `{name, hash, data}` — the exact YAML files the pipeline was built from (`data` again `[]byte` → base64) (model/config.go 19-25; pipeline.go 397-407). Useful to correlate cost with the workflow revision actually used.
- **Pipeline metadata** `GET /repos/{repo_id}/pipelines/{pipeline_number}/metadata` (MustPush → 401 for this token) → the `metadata.Metadata` object incl. `prev` pipeline.
- **Queue** `GET /queue/info` — **admin only** (`queue.Use(session.MustAdmin())`, router 184-190; live 401 with this token). Returns `InfoT{pending[], waiting_on_deps[], running[], stats{worker_count, pending_count, waiting_on_deps_count, running_count}, paused}` (server/queue/queue.go 72-84), each task `{id, pid, name, labels, dependencies, run_on, dep_status, agent_id, pipeline_id, repo_id, concurrency_limit, concurrency_group, created}` (model/task.go). Also admin-only: `GET /pipelines` (queue feed, `Feed[]` with `created/started/finished`), `GET /agents/{agent_id}/tasks`, `POST /queue/pause|resume`.
- **Restart / cancel**: `POST /repos/{id}/pipelines/{n}` (MustPush; restart with env overrides, §3.3), `POST …/cancel` (MustPush).
- **Prometheus** (server docs §Metrics): `/metrics` with `WOODPECKER_PROMETHEUS_AUTH_TOKEN`; `woodpecker_pipeline_time` (per repo/branch/status, and per workflow for multi-workflow pipelines), `woodpecker_step_duration_seconds` histogram, `woodpecker_pending_steps`, `woodpecker_running_steps`, `woodpecker_waiting_steps`, `woodpecker_worker_count` — server-side setting, not checked live.
- Token capabilities observed live: `GET /api/repos/1/permissions` → `{"pull":true,"push":false,"admin":false}`; `GET /api/user` → 401 "User not authorized" (unexpected for a personal token — not explained by the sources read; noted in the final section).

## 11. Agent configuration for a shared single-host agent

- `WOODPECKER_MAX_WORKFLOWS` (legacy alias `WOODPECKER_MAX_PROCS`), default `1`, "agent parallel workflows" / docs: "Configures the number of parallel workflows." (cmd/agent/core/flags.go; agent docs §Workflows per agent — example value 4). Each workflow slot runs its steps sequentially unless step `depends_on` makes a DAG, and each of this repo's push/PR pipelines enqueues five or six workflows at once, so with `MAX_WORKFLOWS=4` two workflows always wait (pipeline `started` vs workflow `started` in §10 quantifies it).
- `WOODPECKER_AGENT_LABELS` (legacy alias `WOODPECKER_FILTER_LABELS` — source comment "remove WOODPECKER_FILTER_LABELS in v4.x"; CLI flag `--labels`, alias `--filter`): "List of labels to filter tasks on. An agent must be assigned every tag listed in a task to be selected." Docs: `key=value,second-key=*`; "`*` can be used as a wildcard. If you use `!` as key prefix it is mandatory for the workflow to have that label set (without !) set and matched." (3.11.0 "Allow agents to require labels on workflows [#5633]"). Default agent labels: `platform=os/arch`, `hostname=<name>`, `backend=docker`, `repo=*`; every workflow carries at least `repo=<owner>/<repo>` (and internal `woodpecker-ci.org/*` labels, builder.go). Workflow side: `labels:` map; "An agent takes up a workflow and executes it if **every** label assigned to it matches the label of the agent." Server-side default for unlabeled workflows: `WOODPECKER_DEFAULT_WORKFLOW_LABELS` (3.0.0 #4326). With a single agent, labels only matter if a second agent is added; `!`-prefixed labels would let a dedicated agent refuse unlabeled work.
- `WOODPECKER_AGENT_SINGLE_WORKFLOW` (exit after one workflow, forces MAX_WORKFLOWS=1), `WOODPECKER_HOSTNAME`, `WOODPECKER_BACKEND` (`auto-detect|docker|local|kubernetes`), `WOODPECKER_HEALTHCHECK[_ADDR]` (`:3000`), `WOODPECKER_RETRY_TIMEOUT` (2m), `WOODPECKER_LOG_ENTRY_STREAM_BUFFER_SIZE` (100).
- Docker-backend resource knobs — **agent-wide, applied identically to every step container** (`toHostConfig` sets `container.Resources{CPUQuota, CPUShares, CpusetCpus, Memory, MemorySwap}` and `ShmSize` from the agent config for each step; docker/convert.go 80-96): `WOODPECKER_BACKEND_DOCKER_LIMIT_MEM` (bytes, 0 = no limit), `…_LIMIT_MEM_SWAP`, `…_LIMIT_SHM_SIZE`, `…_LIMIT_CPU_QUOTA` ("microseconds per CPU period"), `…_LIMIT_CPU_SHARES` ("relative weight vs. other containers"), `…_LIMIT_CPU_SET` (e.g. `1,2`); legacy aliases `WOODPECKER_LIMIT_*` still accepted (docker/flags.go). Moved from server to agent in 3.0.0 ("Move docker resource limit settings from server to agent [#3174]"). Other docker knobs: `…_NETWORK` (attach an existing network to all step containers — "allows the containers of different pipelines to access each other!"), `…_VOLUMES`, `…_APPARMOR_PROFILE`, `…_STOP_TIMEOUT` (20 s; 3.14.0 #6445), `…_HOST`, `…_API_VERSION`, `…_ENABLE_IPV6`.
- **Per-step resource limits in YAML: none for the docker backend.** `backend_options.docker` decodes into `BackendOptions{User string}` only (docker/backend_options.go 24-26); the docker backend docs' "Step specific configuration" section documents only "Run user" (`backend_options: docker: user: 65534:65534`). Memory/CPU per step exist only for the Kubernetes backend (`backend_options.kubernetes.resources`, out of scope). Concurrency pressure on the shared host therefore has to be managed by `WOODPECKER_MAX_WORKFLOWS`, the agent-wide limits above, in-step choices (the repo's `-n 4`), or `concurrency:` limits per workflow (§5.1).
- Pipeline timeout: repo `timeout` (minutes; server defaults `WOODPECKER_DEFAULT_PIPELINE_TIMEOUT=60`, cap `WOODPECKER_MAX_PIPELINE_TIMEOUT=120`; "Do not allow 0 minute timeout [#6903]" 3.17.0) is sent to the agent per workflow (`rpc.Workflow{Timeout: repo.Timeout}`, server/pipeline/queue.go 69-73). Repo value: 60.
