phase 11 · the schema was actually wrong

Order-placement request rewritten to Kalshi's current API

The one open question flagged since before this session — "re-verify the order schema before ever flipping trading_enabled" — turned out to have a real answer, and it wasn't reassuring. Fetched docs.kalshi.com directly (not a changelog, the live pages) and found the implementation targeted Kalshi's legacy order surface: POST /portfolio/orders with action+side("yes"/"no")+integer-cents yes_price/ no_price. Current docs show the endpoint moved to POST /portfolio/events/orders, collapsed action+side into one side field ("bid"/"ask" — there's no "no" value; selling YES and buying NO are the same order-book trade), switched count/price to strings instead of integer cents, and added two newly-required fields (time_in_force, self_trade_prevention_type) with no equivalent in the old shape. Kalshi's own docs note the legacy endpoint's migration deadline was "no earlier than May 6, 2026" — already past by the time this was checked — meaning the old code could have been silently rejected the first time it was ever actually used. Read endpoints (balance/positions/fills) were also checked against current docs and are unchanged. Rewrote create_order/cancel_order to the current shape; 4 new tests verify the exact request (path, method, every body field) against a faked HTTP client — no network call, no real credentials, and trading_enabled stays false throughout. Still true, and still worth repeating: no live order has ever actually been placed with this code.

phase 13 · a real key, finally

Connected a real account — and the auth signing itself was broken

The last open P0 item needed something no amount of code review could substitute for: an actual Kalshi API key. Once one existed, connecting it immediately 401'd — on both production and demo hosts, ruling out an environment mismatch. Fetched Kalshi's own worked authentication example directly from docs.kalshi.com (path='/trade-api/v2/portfolio/balance') and found the bug: this file's signed message omitted the /trade-api/v2 prefix that path is supposed to include. The request URLs were always correct — only the signature input was wrong, which is exactly the kind of bug that produces a clean 401 with no other symptom, and exactly why this had sat unverified for so long: there was never a real key to notice with before. Fixed by deriving the correct base path from base_url itself (urlsplit(base_url).path) rather than hardcoding it a second time, so it stays correct however base_url is configured. Along the way, discovered demo and production Kalshi environments need separate credentials entirely — added KALSHI_ACCOUNT_BASE_URL so the account client can target either independently of the public market-data client, which stays on production. With auth actually working, the real response shapes finally settled the other half of this roadmap item: several guessed field names were wrong (position_fp not position, market_exposure_dollars not market_exposure, count_fp/yes_price_dollars/ no_price_dollars on fills, not count/price) and silently rendered blank for every row before now. Also found that "balance" and "portfolio_value" are two genuinely different real numbers (cash vs. cash-plus-positions) that the dashboard had been treating as interchangeable fallbacks for each other — now shown side by side, explicitly labeled. phase 15 · the SDK detour, reversed — with more evidence

Full migration to the official SDK, once "decided against it" turned out to be a version artifact

Pushed back on: "the SDK shouldn't be crashing, investigate further" — phase 14's conclusion was real but incomplete. pip index versions had silently resolved kalshi_python_async to 3.2.0 under Python 3.11 with no warning that newer releases existed and needed newer Python; the real PyPI JSON API showed the true latest was 3.27.0, requiring Python ≥3.13, and matching Kalshi's current OpenAPI spec exactly. Bumped the Dockerfile to python:3.13-slim, pinned the exact SDK version (plus urllib3, an undeclared dependency the SDK needs but doesn't list — a real packaging gap on Kalshi's side, found via a genuine ModuleNotFoundError), and re-tested: every read endpoint and order placement worked cleanly against the real connected account. Given the do-over, migrated fully rather than re-verifying the old hand-rolled client — kalshi_client.py and kalshi_account_client.py were rewritten so the SDK owns signing, endpoint paths, and request/response schemas entirely, keeping the same public method signatures and dict-shaped returns so main.py barely changed. Two implementation details that only surfaced by reading the SDK's own generated source, not by guessing from its docs: _request_timeout is accepted by create_order_v2 but rejected outright by every read endpoint and by cancel_order_v2; and the 429 backoff wrapper (phase 14) became dead code the instant Kalshi calls stopped going through raw httpx, so it was rewritten as call_with_backoff to wrap SDK calls directly instead — the SDK's own retry support doesn't cover 429 at all, so this still earns its keep. Whole test suite rewritten around fakes/throwaway keys rather than real credentials.

phase 16 · chasing down the 403s for real

Root-caused the recurring ddev-router 403/404s instead of restarting past them again

This exact site had gone briefly unreachable several times already this session, always "fixed" by a ddev restart — until one restart didn't fix it, which was the signal to stop treating it as noise. Read ddev-router's own generated Traefik config directly (/mnt/ddev-global-cache/traefik/config/<project>_merged.yaml) instead of guessing: it showed two routers with the identical HostRegexp rule on the same https entrypoint — one for the custom fastapi service, one for ddev's default, empty-docroot web service, which every ddev project gets whether it's used or not. Traefik's tie-break between two equal-priority routers isn't stable across reloads, so the site would randomly land on web's empty docroot (→ 403) instead of fastapi. config.yaml's existing router_http_port/router_https_port: "" (an earlier fix attempt, whose own comment described this exact symptom) never actually addressed it — those only set the ports ddev-router itself listens on, not which services get routers generated at all, which is exactly why the problem kept coming back despite it. Real fix: a docker-compose override blanking out web's own HTTP_EXPOSE/HTTPS_EXPOSE/VIRTUAL_HOST so ddev's router-config generator never creates a web router for this hostname in the first place. Verified two ways post-restart: re-read the generated config (web routers for this host: 0, was 3), and 10/10 real external HTTPS requests through the actual router path returned 200. Superseded by phase 17, immediately after — this fix worked, but left web sitting there unused; the next phase gave it an actual job instead.

phase 17 · a real frontend/backend split, not just a router fix

main.py is API-only now — nginx serves the dashboard, fastapi has no public URL at all

Explaining phase 16's fix prompted a fair question: why keep an idle, empty web container around at all instead of actually using it? Turned out main.py was serving the dashboard's HTML directly (FileResponse/StaticFiles) from the same process as the API — not a "frontend service" in any real sense, just one process wearing two hats. Split it for real: removed the /, /status, /login, /accounts routes and the /static mount from main.py entirely, gave web (nginx, docroot: static) the job of serving those pages directly, and had it reverse-proxy /api/ and /auth/ back to fastapi (.ddev/nginx/kalshi-proxy.conf). fastapi dropped its HTTP_EXPOSE/HTTPS_EXPOSE/VIRTUAL_HOST entirely — no public URL of its own anymore, reachable only inside the project's docker network as fastapi:8000. That doesn't just avoid phase 16's router collision, it makes it structurally impossible: there's exactly one service left that could ever register a router for this hostname. It also means the actual thing asked for is now true — a separate frontend could be built against this API later without touching main.py at all. One real correctness catch along the way: nginx's try_files <file> =404 serves a matched file from within its own location block rather than re-entering location matching, so the old NO_CACHE_HEADERS behavior (added earlier after a shipped panel silently failed to appear until a hard refresh) had to be set directly on each page's location block, not inherited from one shared regex block — caught by actually curling each route and checking headers, not assumed. Also added --proxy-headers --forwarded-allow-ips=* to uvicorn, since request.url_for() (the OAuth redirect_uri) now needs to trust a second proxy hop (nginx, in front of ddev-router) to resolve the right scheme/host.

phase 22 · a trade tape scoped to what you're actually watching

Whale Watch gets a real trade tape, deliberately not the whole exchange's

Last drill-down-adjacent item in Phase 0.5's list: a full trade tape, distinct from the per-market drill-down's own recent-trades list built two phases ago. get_trades with no ticker filter returns trades across every market on Kalshi, not just the ones this app is watching - most of that would be noise next to the whale-signal concept the tape ties into, so new _fetch_trade_tape() instead fires one get_trades(ticker=X, limit=5) per watched market concurrently (the same pattern _fetch_markets already uses for its own explicit-watchlist branch), merges, and sorts newest-first. "Make data consumption, storage, and retrieval hyper-efficient" - measured before touching anything

Direct request, but deliberately investigated before implementing anything - the request named "storage" as a concern, and data/*.db turned out to be a red herring: 332KB total, and PRAGMA freelist_count showed most of even signal_log.db's share was empty pages left over from testing phase 27's reset-domains feature minutes earlier, not organic growth. Known Limitations

Every currently open Kalshi market is a multi-leg combo contract
Verified by paginating 500 live open markets from Kalshi's real API — zero simple single-outcome markets exist right now. Titles are formatted as "N-leg parlay: A, B +N more" to stay scannable, but that's the ceiling on readability given the actual data, not a partial fix.
Order-placement request schema was wrong — now fixed (verified 2026-08-07)
This used to be an open question; it turned out the original implementation targeted Kalshi's legacy order shape (POST /portfolio/orders, integer-cents yes_price/ no_price). Fetched docs.kalshi.com directly and found the endpoint moved to POST /portfolio/events/orders, with action+side(yes/no) collapsed into one side field ("bid"/"ask"), string-typed count/price instead of integer cents, and two newly-required fields (time_in_force, self_trade_prevention_type) with no old equivalent. Kalshi's own docs note the legacy endpoint's migration deadline was "no earlier than May 6, 2026" — already past — so the old code could have failed outright the first time it was ever used. Rewritten and covered by 4 tests that verify the exact request shape against a faked HTTP client (no network, no real credentials). Still true: no live order has ever actually been placed with this code, and Kalshi's docs can move again — don't treat this as a permanent guarantee.
No "close position" flow
The paper broker opens positions but nothing ever explicitly closes one — equity reflects mark-to-market unrealized P&L on whatever's still open. There's no realized-P&L concept yet, so none is shown.
Real account connection: verified 2026-08-07, and the auth signing itself was broken
A real key made it possible to test this for the first time, and it surfaced a genuine bug, not just an unconfirmed guess: every signed request 401'd, on both production and demo — the signed message omitted the /trade-api/v2 prefix Kalshi's own docs example includes. Fixed in services/kalshi_account_client.py. Once auth worked, several field-name guesses turned out wrong too — market_positions uses position_fp/market_exposure_dollars, fills use count_fp/yes_price_dollars/no_price_dollars — none of which existed under the old guessed names, so those rows silently rendered blank before. All fixed and verified against a real connected account in a real browser session. Raw JSON stays visible everywhere regardless, since Kalshi's docs can still drift again — this is now confirmed-correct, not guaranteed permanent.
