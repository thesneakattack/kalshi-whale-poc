phase 5 · correctness

Real data, not silently-wrong data

Found that the code was written against Kalshi field names (yes_bid, volume) that don't exist in the live API — it actually returns yes_bid_dollars and volume_24h_fp. That single mismatch had been silently causing four separate bugs: blank prices/volume on the dashboard, a "top volume" sort that was a no-op, whale-signal prices falling back to random numbers instead of real market prices, and momentum/contrarian bias always picking the same side. Fixed all four, then replaced raw tickers everywhere with Kalshi's own human-readable title field, with combo-parlay-aware formatting once it became clear every currently open market is a multi-leg combination contract.

services/kalshi_client.py · services/whale_simulator.py · main.py · static/index.html

phase 8 · durability

Paper account survives a restart

The paper broker (bankroll, open positions, trade log) was the last piece of runtime state still in-memory only — a restart silently reset it back to config/settings.yaml's starting_bankroll while signal_log.py's whale track record kept growing underneath it. Now persists to SQLite the same way. Fixing that surfaced a second, sharper bug: doing it for the broker alone would have kept the recovered bankroll but reset risk_manager.py's daily-loss baseline to config's number on every restart — either mismeasuring today's loss against a stale figure, or silently un-halting a kill switch that had actually tripped. Persisted that alongside it. POST /api/reset now wipes both in place rather than swapping in a new broker object (which would have left stale rows behind and gotten resurrected on the next restart). Verified against the live dev container: placed a real paper trade, ran a full ddev restart, confirmed the exact position/bankroll/trade survived.

services/paper_broker.py (+ data/paper_broker.db) · services/risk_manager.py (+ data/risk_state.db) · main.py (/api/reset)
phase 9 · hardening

CORS tightened, a real test suite, CI wired up

Three P0/P3 roadmap items in one pass, now that the project has a git repo to actually run CI against. allow_origins=["*"] was a leftover from early local-only development — replaced with a default of the DDEV hostname + localhost:8000, overridable via ALLOWED_ORIGINS in .env. Then 35 tests across four files covering paper_broker.py (fill math, cost capping, cooldowns, persistence across a simulated restart), risk_manager.py (kill-switch trip/stay-halted/resume, persistence), strategy_engine.py (every skip/trade branch), and signal_log.py (series grouping, win-rate math, time windows) — each test isolates its own SQLite file via DB_PATH monkeypatching so none of them touch the real data/*.db. Spot-checked the suite wasn't vacuous by deliberately breaking the "no"-side P&L direction and confirming the right test failed before reverting. GitHub Actions now runs the suite on every push/PR.

main.py (CORS) · .env.example · tests/*.py · pytest.ini · requirements-dev.txt · .github/workflows/tests.yml
phase 10 · the confirmation gate

Real trading needs a deliberate, typed confirmation now

Closed the gap the roadmap had flagged since before this session: nothing previously stopped kalshi_account.trading_enabled from being flipped except a comment in config/settings.yaml. POST /api/config now structurally refuses to touch that field at all — the only path is POST /api/trading/enable, which requires a real connected account and a typed, exact-match confirmation phrase ("ENABLE REAL TRADING"), not a checkbox. POST /api/trading/disable is always allowed, no confirmation — turning real trading back off is never the dangerous direction. The dashboard's account bar gets a matching control. Building the frontend piece surfaced a real bug before it shipped: the account bar re-renders from scratch on every 5-second poll, which would have silently wiped the confirmation phrase (and focus) mid-typing — fixed by capturing and restoring the input's value/selection/focus across each re-render. Verified two ways: 8 backend tests exercise every branch (wrong phrase, no account connected, correct phrase, disable) against an isolated copy of config/settings.yaml and the paper broker/risk DBs — not the real, live ones — and a real Chrome session via the project's ddev selenium-chrome service confirmed the gate renders, the confirm button enables only on an exact match, the mid-typing refresh no longer clobbers the input, and a failed backend call surfaces its real error text in the UI.

main.py (/api/trading/enable, /api/trading/disable, /api/config guard) · static/index.html (trading-gate UI) · tests/test_trading_gate.py
phase 11 · the schema was actually wrong

Order-placement request rewritten to Kalshi's current API

The one open question flagged since before this session — "re-verify the order schema before ever flipping trading_enabled" — turned out to have a real answer, and it wasn't reassuring. Fetched docs.kalshi.com directly (not a changelog, the live pages) and found the implementation targeted Kalshi's legacy order surface: POST /portfolio/orders with action+side("yes"/"no")+integer-cents yes_price/ no_price. Current docs show the endpoint moved to POST /portfolio/events/orders, collapsed action+side into one side field ("bid"/"ask" — there's no "no" value; selling YES and buying NO are the same order-book trade), switched count/price to strings instead of integer cents, and added two newly-required fields (time_in_force, self_trade_prevention_type) with no equivalent in the old shape. Kalshi's own docs note the legacy endpoint's migration deadline was "no earlier than May 6, 2026" — already past by the time this was checked — meaning the old code could have been silently rejected the first time it was ever actually used. Read endpoints (balance/positions/fills) were also checked against current docs and are unchanged. Rewrote create_order/cancel_order to the current shape; 4 new tests verify the exact request (path, method, every body field) against a faked HTTP client — no network call, no real credentials, and trading_enabled stays false throughout. Still true, and still worth repeating: no live order has ever actually been placed with this code.

services/kalshi_account_client.py · tests/test_kalshi_account_client.py
phase 12 · shadow mode

The last P0 item: logs intended real trades, executes nothing

The README has called this a prerequisite to live trading since before this project had git history — now built. services/shadow_mode.py's ShadowTrader runs the identical follow-the-whale gates strategy_engine.py uses (confidence threshold, whale win-rate filter, cooldown, position-size-rounds-to-zero) but sized against a real reference bankroll instead of the paper broker's — the connected account's actual balance when one exists, or risk.starting_bankroll as a clearly-labeled fallback when it doesn't, so this is meaningfully testable without a real Kalshi account connected. It gets its own independent daily-loss kill switch, deliberately not shared with paper trading's — sharing one would have meant a real-bankroll shadow loss silently halting the paper strategy too, or vice versa. Every gate only ever writes to data/shadow_mode.db; nothing in this path can call create_order. Active whenever mode is shadow or live — previously a YAML field nothing actually read; now a real Controls-panel dropdown. Portfolio view gets a Shadow Trades panel explaining itself in the same plain-English register as the rest of the beginner-facing UI. 10 tests cover every gate in isolation; live-verified end to end against the running app — flipped it to mode: shadow, watched a real intended-trade row appear with the correct fallback-bankroll label, confirmed the Controls dropdown and Portfolio panel both rendered it correctly in a real Chrome session, then reverted the live app back to paper and reset the paper broker (depleted from this session's extended live testing) before finishing.

services/shadow_mode.py · main.py (_shadow_reference_bankroll, /api/state shadow key) · static/index.html (Shadow Trades panel, Mode dropdown) · tests/test_shadow_mode.py
phase 13 · a real key, finally

Connected a real account — and the auth signing itself was broken

The last open P0 item needed something no amount of code review could substitute for: an actual Kalshi API key. Once one existed, connecting it immediately 401'd — on both production and demo hosts, ruling out an environment mismatch. Fetched Kalshi's own worked authentication example directly from docs.kalshi.com (path='/trade-api/v2/portfolio/balance') and found the bug: this file's signed message omitted the /trade-api/v2 prefix that path is supposed to include. The request URLs were always correct — only the signature input was wrong, which is exactly the kind of bug that produces a clean 401 with no other symptom, and exactly why this had sat unverified for so long: there was never a real key to notice with before. Fixed by deriving the correct base path from base_url itself (urlsplit(base_url).path) rather than hardcoding it a second time, so it stays correct however base_url is configured. Along the way, discovered demo and production Kalshi environments need separate credentials entirely — added KALSHI_ACCOUNT_BASE_URL so the account client can target either independently of the public market-data client, which stays on production. With auth actually working, the real response shapes finally settled the other half of this roadmap item: several guessed field names were wrong (position_fp not position, market_exposure_dollars not market_exposure, count_fp/yes_price_dollars/ no_price_dollars on fills, not count/price) and silently rendered blank for every row before now. Also found that "balance" and "portfolio_value" are two genuinely different real numbers (cash vs. cash-plus-positions) that the dashboard had been treating as interchangeable fallbacks for each other — now shown side by side, explicitly labeled. Verified against a real connected account holding real open positions and fill history, in a real Chrome session, not just curl.

services/kalshi_account_client.py (_base_path) · main.py (KALSHI_ACCOUNT_BASE_URL) · static/index.html (real position/fill rendering, Cash Balance/Portfolio Value split) · .env.example · tests/test_kalshi_account_client.py
phase 14 · SDK detour, and two small hardenings

Evaluated the official SDK, decided against it — with receipts

A real key made deeper API research worthwhile too. Investigated switching to Kalshi's official, async-native kalshi_python_async SDK — it would remove hand-rolled request-signing as a bug class entirely, which felt appealing right after finding and fixing exactly that kind of bug. Installed it and pointed it at the real connected account rather than deciding from documentation alone: it authenticates fine, but get_positions() and get_fills() both threw Pydantic ValidationError — its models require integer fields Kalshi's live API no longer sends, only the same _fp/_dollars string fields this project's own client already handles correctly. Confirmed by reading the raw response through the SDK's own escape hatch, not just trusting the traceback. Decided to stay on the hand-rolled client. One nice side effect: the SDK's own auth source hardcodes the identical /trade-api/v2 signed-path prefix this session's earlier auth fix added — independent, from-the-source confirmation that fix was exactly right.

Also shipped two smaller findings from the same documentation pass: exponential backoff on 429 (Kalshi's own rate-limit docs ask for this; nothing previously did it), shared by both Kalshi clients via a new request_with_backoff; and a header badge surfacing Kalshi's real exchange open/closed status, so a quiet signal feed reads as "market's closed," not "strategy's stuck."

Known Limitations

Every currently open Kalshi market is a multi-leg combo contract
Verified by paginating 500 live open markets from Kalshi's real API — zero simple single-outcome markets exist right now. Titles are formatted as "N-leg parlay: A, B +N more" to stay scannable, but that's the ceiling on readability given the actual data, not a partial fix.
Order-placement request schema was wrong — now fixed (verified 2026-08-07)
This used to be an open question; it turned out the original implementation targeted Kalshi's legacy order shape (POST /portfolio/orders, integer-cents yes_price/ no_price). Fetched docs.kalshi.com directly and found the endpoint moved to POST /portfolio/events/orders, with action+side(yes/no) collapsed into one side field ("bid"/"ask"), string-typed count/price instead of integer cents, and two newly-required fields (time_in_force, self_trade_prevention_type) with no old equivalent. Kalshi's own docs note the legacy endpoint's migration deadline was "no earlier than May 6, 2026" — already past — so the old code could have failed outright the first time it was ever used. Rewritten and covered by 4 tests that verify the exact request shape against a faked HTTP client (no network, no real credentials). Still true: no live order has ever actually been placed with this code, and Kalshi's docs can move again — don't treat this as a permanent guarantee.
No "close position" flow
The paper broker opens positions but nothing ever explicitly closes one — equity reflects mark-to-market unrealized P&L on whatever's still open. There's no realized-P&L concept yet, so none is shown.
Real account connection: verified 2026-08-07, and the auth signing itself was broken
A real key made it possible to test this for the first time, and it surfaced a genuine bug, not just an unconfirmed guess: every signed request 401'd, on both production and demo — the signed message omitted the /trade-api/v2 prefix Kalshi's own docs example includes. Fixed in services/kalshi_account_client.py. Once auth worked, several field-name guesses turned out wrong too — market_positions uses position_fp/market_exposure_dollars, fills use count_fp/yes_price_dollars/no_price_dollars — none of which existed under the old guessed names, so those rows silently rendered blank before. All fixed and verified against a real connected account in a real browser session. Raw JSON stays visible everywhere regardless, since Kalshi's docs can still drift again — this is now confirmed-correct, not guaranteed permanent.
